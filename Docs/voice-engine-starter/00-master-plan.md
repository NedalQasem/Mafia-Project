## 1. الملخص التنفيذي

**المشكلة:** الصوت عصب كل ألعابنا الاجتماعية. الاعتماد على خدمة طرف ثالث (EOS Voice، Agora، Vivox...) معناه حدود، اشتراكات، وقيود على الشكل والقواعد. و«LiveKit» رغم إنه مفتوح المصدر وعنا على السيرفر، لسا برنامج غيرنا: ما بنتحكم ببروتوكوله ولا بسلوكه على الموبايل.

**الحل:** نبني محرك صوت بروتوكوله ملكنا، **مكتبة نواة واحدة (Core)** بلغة بتشتغل على كل المنصات، مع طبقات ربط رقيقة لكل محرك ومنصة، وسيرفر ترحيل صوت (SFU) صغير وخفيف. أي لعبة جديدة بتاخد «حزمة» جاهزة (Unity package أو Unreal plugin أو JS) وبتربط بسطور قليلة.

**المبادئ:**
1. **الجودة قبل الميزات:** صدى ضجيج تأخير انقطاع = لعبة ميتة. هدفنا صوت «مثل مكالمة» على موبايل متوسط وشبكة سيئة.
2. **الواجهة ثابتة والتنفيذ قابل للتبديل:** لعبتنا بتحكي مع `IVoiceService` (موجود فعلاً). نقدر نبدّل LiveKit ↔ MenaGamingVoiceCore بسطر إعداد، وبنقدر نرجع فوراً.
3. **السيرفر يقرر القواعد، العميل ينفّذ:** من يحكي؟ من يسمع من؟ (ليل المافيا). كلها أوامر موقّعة من سيرفر اللعبة، مش من الجهاز (تحاشي الغش).
4. **ملكية كاملة:** كل مكتبة نستخدمها داخل النواة ترخيصها متساهل (BSD/MIT/Apache)، ما في GPL، وما في خدمة خارجية وقت التشغيل.
5. **نقيس كل شي:** ما في «بيبان إنه تمام». في أرقام وبوابات.

**ما الجديد مقابل LiveKit (ليش يستاهل):** هجرة الشبكة بدون إعادة دخول (Wi-Fi↔بيانات)، قواعد الصوت من السيرفر بدون إعادة اتصال (حل «ارفع إيدك» الحالي)، بروتوكول أخف على البطارية والداتا، بدون توقف لو تغيّر مزوّد، وتحكم كامل بالأخطاء.

**الصدق عن الصعوبة:** الجزء الصعب مش الشبكة، **صدى الصوت (AEC) وتنوّع أجهزة أندرويد**. هاد اللي بياخد أغلب الوقت والتجارب. الخطة مبنية حواليه.

## 2. الأهداف والمقاييس

### 2.1 أهداف (Goals)
- صوت غرف (مستمعون كثر ومتكلمون قلة) حتى **٦٤+ مستمع / ٨ متكلمين** بالغرفة، وصوت مباريات (≤ ١٦) بقواعد خاصة.
- **موبايل أولاً:** Android ثم iOS، **ثم** Windows/Steam (+Steam Deck/Linux)، **ثم** Web.
- محركات: Unity (الأولوية الأولى)، Unreal (الثانية)، ومكتبة C عامة لأي محرك آخر.
- تكلفة تشغيل منخفضة: VPS واحد يخدم مئات المتكلمين المتزامنين.
- خصوصية: تشفير، بدون تسجيل صوت افتراضياً.

### 2.2 مش أهداف (Non-goals) بالنسخة الأولى
- فيديو، مشاركة شاشة، SIP/هاتف، تسجيل سحابي، ترجمة، صوت مكاني ثلاثي الأبعاد كامل (بنصمم له الباب بس).
- E2EE (تشفير من طرف لطرف): بنصمم له مكان (SFrame لاحقاً). النسخة الأولى: تشفير بين الجهاز والسيرفر.
- توافق مع WebRTC (ما رح نبني WebRTC).

### 2.3 مقاييس النجاح (KPIs) — أرقام ملزمة

| المقياس | الهدف | القياس |
|---|---|---|
| تأخير «من الفم للأذن» (p50 / p95) | ≤ 200 / ≤ 350 ms | جهازين + حزمة اختبار بالتصفيق (loopback ملحوظ بالـCLI) |
| نجاح الانضمام | ≥ 99% خلال 1.5 ث (p95) | تيليمتري العميل |
| الانقطاع | ≤ 0.5 مرة/ساعة/لاعب | تيليمتري + اختبار تحمّل ٢ ساعة |
| تحمّل ضياع الحزم | جودة مقبولة حتى 10% ضياع عشوائي، و20% مع FEC | محاكاة شبكة (netem) |
| صدى متبقٍ | ERLE ≥ 25 dB بالمتوسط (بدون سماعات) | اختبار آلي + أذن بشرية |
| استهلاك المعالج | ≤ 8% من معالج واحد (موبايل متوسط) أثناء الكلام | Profiler |
| الداتا (متكلم واحد) | ≤ 48 kbps فعلياً (24 kbps ترميز) + DTX | عدّاد |
| البطارية | ≤ 4%/ساعة إضافية (شاشة مطفية بالمقارنة) | جهاز حقيقي |
| جودة الإدراك (MOS) | ≥ 4.0 (ViSQOL) على سيناريوهات الاختبار | أداة ViSQOL |
| قدرة السيرفر | ≥ 20,000 حزمة/ث على vCPU واحد | أداة الحمل |

## 3. حالات الاستخدام الأساسية

1. **غرفة سهرة:** ١–٨ متكلمين، باقي الناس مستمعين. الأدمن/المضيف يرفع ويخفّض من على المايك فوراً (بدون إعادة اتصال).
2. **غرفة رسمية (٦٤+):** نفس الشي مع أدمن؛ مستمعون بدون نشر.
3. **مباراة مافيا (≤ ١٦):** النهار الكل يحكي، الليل صمت ما عدا المافيا لبعض، الأموات يسمعوا بس.
4. **دردشة فريق/ثنائي** (ألعاب ثانية): غرف صغيرة «push-to-talk» أو مفتوحة.
5. **لاحقاً:** صوت مكاني بالألعاب ثلاثية الأبعاد، مذيع/جمهور، إشراف (كتم/طرد/تقرير).

**قواعد مشتركة:** الكتم المحلي لشخص (عندي)، كتم الكل (السماعة)، مؤشر «عم يحكي» لكل لاعب، تحكم بالحجم لكل لاعب، push-to-talk اختياري، كتم من الأدمن (سيرفر)، الطرد.

## 4. القرارات المعمارية (ADR)

> كل قرار: **القرار · السبب · البدائل المرفوضة · متى نراجعه.**

**ADR-1: SFU (ترحيل بدون خلط) مش P2P ومش MCU.**
- السبب: P2P mesh بينهار فوق ٤–٥ لاعبين وبيكشف عناوين اللاعبين. MCU (خلط الصوت بالسيرفر) بياكل معالج ويضيف تأخير. SFU: السيرفر بيمرّر الحزم بس، رخيص وسريع.
- مراجعة: لو احتجنا غرف ضخمة جداً (آلاف مستمعين) نضيف طبقة توزيع (cascading SFU).

**ADR-2: بروتوكول ملكنا فوق UDP، مش WebRTC.**
- السبب: WebRTC ضخم (ICE/DTLS/SRTP/SDP) ونحتاج مكتبة ضخمة (libwebrtc) لكل منصة = اعتماد وحجم (>10 MB) وصعوبة ربط Unreal/Web. بروتوكول بسيط (حزمة صوت + تحكم) بنقدر نبنيه ونختبره ونسيطر عليه.
- البدائل: WebRTC (LiveKit/mediasoup) — ما بنتحكم؛ QUIC datagrams — جيد لكن دعم الموبايل/المحركات لسا غير ناضج لوقت التشغيل الحي (نراجعه بالنسخة 2).
- **التضحية:** ما في «ICE/TURN» جاهز. تعويضه: السيرفر على IP عام (العميل هو اللي بيبدأ) + بديل TCP/WebSocket (قسم 6.4).

**ADR-3: النواة بلغة Rust، بواجهة C ثابتة (C ABI).**
- **✅ اعتمده المالك (2026-11-02): Rust للنواة وللسيرفر معاً (ADR-3 + ADR-11).**
- السبب: بدنا كود **بدون GC** للصوت الحي (Unity C# فيه GC يعمل تقطيع)، آمن للذاكرة، يترجم لكل المنصات (Android/iOS/Windows/Linux/macOS/WASM)، ومكتبة واحدة تخدم Unity (P/Invoke) وUnreal (C++) وWeb (WASM) بدون إعادة كتابة.
- البدائل: C++ (مألوف بـUnreal لكن أخطر)، C#/.NET (NativeAOT) — GC ومشاكل الوقت الحقيقي بالموبايل.
- **ملاحظة حالة الجهاز:** على جهاز التطوير الحالي مثبّت .NET وNode وDocker، **ما في Rust/CMake/Go**. المرحلة 0 بتثبّتهم (`winget install Rustlang.Rustup`, `cargo install cargo-ndk`, وNDK من Unity أو Android Studio).

**ADR-4: الترميز Opus 48 kHz mono، إطار 20 ms.**
- الافتراضي 24 kbps VBR مقيّد، DTX مفعّل، FEC داخل الحزمة، تعقيد 5 على الموبايل. ملفات: 16 (توفير) / 24 (عادي) / 32 (عالي). Opus مرخّص BSD ومعيار عالمي.

**ADR-5: معالجة الصوت (AEC/NS/AGC) — برمجية داخل النواة + بديل المنصة.**
- الافتراضي: **WebRTC Audio Processing Module (APM)** المستقل (مكتبة `webrtc-audio-processing`، BSD-3) فيه AEC3 وNS وAGC2. ننقل مرجع الصدى من تشغيلنا نحن (لأننا نملك مسار التشغيل).
- البديل حسب المنصة: Android `VoiceCommunication` (AEC العتاد حيث متوفر وجيد)، iOS `VoiceProcessingIO`، Web `getUserMedia({echoCancellation:true,...})`. **اختيار لكل جهاز** من «قاعدة ملفات الأجهزة» (قسم 8.3).
- السبب: AEC العتاد على أندرويد متفاوت حسب الشركة المصنّعة؛ البرمجي بيعطينا اتساق.

**ADR-6: إدخال/إخراج الصوت الأصلي (Native) يتجاوز محرك الصوت بالمحرك.**
- Android: **Oboe** (Apache-2). Windows: WASAPI (عبر `miniaudio`, MIT-0). iOS/macOS: AudioUnit. Web: AudioWorklet.
- السبب: تأخير أقل + AEC سليم (بنتحكم بالمرجع). **وضع اختياري** لتغذية صوت اللاعبين لـ`AudioSource` (للصوت المكاني) بتكلفة تأخير وصدى أعلى.

**ADR-7: قناتين: تحكم موثوق (WebSocket/TLS) + وسائط غير موثوقة (UDP).**
- التحكم: انضمام، قائمة الحضور، أذونات، أوامر كتم/طرد/فلتر استماع، ping. الوسائط: UDP مشفّر. وإذا UDP محجوب: الوسائط تمر على نفس الـWebSocket (أبطأ لكن يشتغل).

**ADR-8: تشفير قفا-بقفا (hop-by-hop) AEAD، بمفاتيح جلسة من التوكن.**
- ChaCha20-Poly1305 (سريع بدون عتاد خاص). السيرفر بيفك ويعيد التشفير لكل مستمع (تكلفة معالج بسيطة). E2EE لاحقاً.

**ADR-9: هجرة المسار (Connection migration) مدمجة.**
- الجلسة معرّفة بـ`session_id` + تشفير، مش بعنوان IP/Port. لو الجهاز بدّل الشبكة، أول حزمة صحيحة من العنوان الجديد بتحدّث مسار الجلسة. **هاد بيحل جذرياً نوع الانقطاع اللي شفناه بسجل LiveKit.**

**ADR-10: قواعد الصوت سلطتها لسيرفر اللعبة.**
- سيرفر اللعبة (مثل `rewards-api` عنا) بيحمل مفتاح موقّع ويرسل للسيرفر الصوتي أوامر (إدارة أذونات النشر/الاستماع). العميل ما بيقدر يتجاوزها.

**ADR-11: السيرفر بـRust كمان (monorepo واحد، بروتوكول مشترك).**
- سبب: نفس كود التعامل مع الحزم والتشفير بالجهتين = أخطاء أقل. أداء ممتاز على معالج واحد. (بديل مقبول: Go. بس Rust بيعطي مكتبة مشتركة.)

### 5.2 نموذج الخيوط (Threading) — قاعدة ذهبية
1. **خيط الصوت (Realtime):** ممنوع فيه تخصيص ذاكرة أو قفل أو I/O أو سجلات. بيتواصل مع غيره بطوابير بدون أقفال (SPSC ring buffers).
2. **خيط الشبكة:** UDP/TCP، التشفير، الـjitter buffer (إدخال).
3. **خيط التحكم:** WebSocket، حالة الاتصال، إعادة المحاولة.
4. **خيط اللعبة (Main):** بيستدعي `mgvc_poll_events()` فقط ويستقبل أحداثاً (بدون callbacks من خيوط أجنبية = أمان مع IL2CPP والـGC).

## 6. البروتوكول (ملخص؛ التفاصيل بالملحق أ)

### 6.1 دورة الاتصال
1. اللعبة بتطلب **توكن** من سيرفرها (`POST /v1/voice/token {room}`، **نفس العقد الحالي**): بيرجع `{url, token, room, canPublish}`.
2. العميل بيفتح WSS على `url` ويرسل `join{token, device_info, protocol_versions}`.
3. السيرفر بيتحقق (توقيع، انتهاء، غرفة)، بيرد `welcome{session_id, udp_host, udp_port, keys, room_state, ice_config?}`.
4. العميل بيرسل **UDP HELLO** مشفّر؛ السيرفر بيرد **UDP WELCOME** → المسار جاهز (3 محاولات × 300 ms وإلا يتحول لوضع TCP).
5. صوت جاري. ping/pong كل 5 ث. تقارير جودة كل ثانية.
6. **هجرة:** أي حزمة صالحة من عنوان جديد = تحديث المسار (مع تحقق «تحدّي» خفيف لمنع الانتحال).
7. الخروج: `bye` أو انتهاء مهلة (15 ث بدون ping).

### 6.2 حزمة الصوت (UDP)
- ترويسة 16 بايت (client→server) / 20 بايت (server→client) + حمولة Opus (~60 بايت عند 24 kbps) + وسم AEAD 16 بايت.
- فيها: نوع/إصدار، أعلام (DTX، بداية كلام)، **مستوى الصوت (للتحديد النشط)**، تسلسل، ختم زمني، معرّف الجلسة/المصدر.
- حد الحجم: **≤ 1200 بايت** (بدون تجزئة IP). ~50 حزمة/ث لكل متكلم.

### 6.3 التحكم عبر قنوات موثوقة (JSON أو CBOR)
رسائل: `join`, `welcome`, `peer_joined/left`, `peer_state{muted,publishing}`, `permissions{can_publish, can_listen_to[]}`, `kick`, `mute{by_admin}`, `ping`, `error{code}`. كلها مرقّمة الإصدار.

### 6.4 وضع TCP/WebSocket البديل
- لو UDP محجوب (بعض الشبكات): نفس حزم الصوت مغلّفة بإطارات ثنائية على الـWebSocket. أبطأ وفيه head-of-line blocking؛ بنعوّض بـjitter buffer أكبر وبتقليل الجودة تلقائياً. يظهر للمطوّر كـ`transport=tcp` بالتيليمتري.

### 6.5 اختيار المتكلمين النشطين
- كل حزمة فيها `level`. السيرفر يحتفظ لكل مستمع بأعلى **N** (افتراضي 4–6) متكلمين نشطين ويمرّر حزمهم، والباقي يُحجب. يوفر الداتا والمعالج ويمنع فوضى ٨ أصوات معاً.

## 7. السيرفر (mgvc-server)

- **المكوّنات:** مستمع UDP (tokio + `socket2` مع `recvmmsg/sendmmsg` على لينكس)، مستمع WSS، جدول الغرف (room → peers)، محقق التوكن، واجهة إدارة HTTP (أذونات)، مقاييس Prometheus، سجل منظم (JSON).
- **التحقق:** توكن JWT موقّع (HS256 مبدئياً بنفس مفتاح `voice.js` الحالي، ثم Ed25519). حقول: `sub`(هوية)، `room`، `exp`، `canPublish`، `canListen`، `name`.
- **الأذونات الحية:** `POST /admin/v1/rooms/{room}/peers/{id}/permissions` موقّع بـHMAC (من سيرفر اللعبة). يطبق فوراً ويبث للعميل. **بيحل مشكلة «اقعد على المقعد → أعد الاتصال بتوكن جديد»** الحالية.
- **الحماية:** حدود لكل IP، حد معدل حزم لكل جلسة، منع التضخيم (رد HELLO أصغر من الطلب قبل التحقق)، مهل، حجم نافذة إعادة الإرسال، قائمة سوداء مؤقتة.
- **الحالة:** بالذاكرة (ما في قاعدة بيانات). لو انطفى السيرفر، العملاء بيرجعوا بنفس التوكن (ما دام صالح).
- **السعة (تقدير للتحقق بالأداة):**
  - الحزمة الكاملة لمتكلم واحد ≈ 92 بايت + 28 (UDP/IPv4) = **120 بايت × 50/ث ≈ 48 kbps**.
  - غرفة ٦٤ مستمع × ٣ متكلمين نشطين = ١٩٢ مجرى ≈ **9.2 Mbps ≈ 4.1 GB/ساعة**.
  - باقة 4 TB/شهر ≈ 970 ساعة من هالذروة؛ الواقع أقل بكثير بفضل DTX (فترات الصمت).
  - معالج: ~10,000 حزمة/ث خارجة لهالغرفة؛ هدفنا ≥ 20,000 حزمة/ث/vCPU. **نقيس بأداة الحمل بالمرحلة 5.**

## 8. العميل (mgvc-core)

### 8.1 مسار الإرسال
`التقاط (10 ms) → APM (AEC+NS+AGC) → VAD/DTX → Opus encode (20 ms) → AEAD → UDP`.
- **PTT / كتم:** عند الكتم نوقف الإرسال (نرسل علم DTX بس).
- **التكيّف:** من تقارير المستقبل (ضياع/jitter) نغيّر معدل البت (16–32 kbps) ونسبة FEC.

### 8.2 مسار الاستقبال
`UDP → AEAD verify → مخزن jitter لكل مصدر → Opus decode (+PLC) → خلط + حجم/كتم لكل لاعب → تشغيل (+ مرجع للـAEC)`.
- **Jitter buffer:** تكيّفي، هدف 40–120 ms، يستخدم إخفاء الضياع (PLC) من Opus، وتمديد/ضغط زمني خفيف عند الحاجة.
- **حد الخلط:** N مصدر معاً (افتراضي 6)، الأعلى مستوى أولاً.

### 8.3 «قاعدة ملفات الأجهزة» (Device Profiles) — سر الاستقرار على أندرويد
ملف JSON بيرتبه سيرفرنا (config عن بعد): لكل `(manufacturer, model, androidSdk)` إعدادات: AEC (برمجي/عتاد/معطّل)، تأخير الإخراج المقدّر، حجم الـburst، وضع Oboe، مصدر الالتقاط، حيل (Workarounds). تبدأ فاضية بقيم افتراضية آمنة، وتكبر بالتجارب. **كل شكوى «صدى» = سطر جديد بالملف.**

### 8.4 الصوت على الموبايل (نقاط حرجة)
- **Android:** `RECORD_AUDIO` + `MODIFY_AUDIO_SETTINGS`؛ Oboe بـ`Usage::VoiceCommunication`؛ التعامل مع `AudioFocus` (مكالمات، تطبيقات أخرى)؛ تبديل السماعة/الأذن/Bluetooth (SCO/HFP: 16 kHz!)؛ خدمة أمامية (Foreground Service من نوع microphone) إذا بدنا الصوت بالخلفية؛ Doze/توفير الطاقة؛ تغيّر الشبكة.
- **iOS:** `AVAudioSession` بوضع `playAndRecord` + `voiceChat`؛ مقاطعات المكالمات؛ أذونات؛ إدارة الخلفية (`audio` background mode).
- **Windows/Steam:** WASAPI بفئة communications؛ تغيّر الجهاز الافتراضي أثناء اللعب؛ جودة سماعات الألعاب.
- **Web:** `getUserMedia`، `AudioWorklet`، سياسات تشغيل تلقائي، `SharedArrayBuffer` يحتاج ترويسات `COOP/COEP`.

## 13. الأمن والخصوصية

- **تشفير** AEAD لكل الحزم + TLS للتحكم. مفاتيح الجلسة من `welcome` فقط (لا تُرسل بالـUDP).
- **توكن قصير العمر** (دقائق للاتصال، تجدد صامت) + ربط بالغرفة والهوية.
- **منع الغش:** كل القواعد بالسيرفر؛ العميل المعدّل ما بيقدر يسمع/يحكي أكثر من المسموح.
- **الخصوصية:** ما في تسجيل افتراضي. السجلات بدون محتوى صوت وبمعرّفات مجزّأة. نص سياسة الخصوصية لازم يذكر الصوت.
- **الإشراف:** كتم/طرد من الأدمن (سيرفر). «سجل قصير عند البلاغ» (ring buffer اختياري) فقط بعد قرار قانوني/موافقة صريحة (**قرار منتج مؤجل**).
- **هجمات:** DoS/تضخيم (قسم 7)، إعادة تشغيل الحزم (نافذة replay)، تلاعب بالتسلسل، حزم مشوّهة (fuzzing إلزامي).
- **أطفال:** إن استهدفنا قاصرين تفعيل قيود (COPPA/ما يماثلها) — **سؤال مفتوح**.

## 14. بوابات الاستبدال (متى نشيل LiveKit)

لا نستبدل ولا نخفف الاعتماد إلا بعد **كل** الشروط، على الأقل ٢ أسبوع بيتا داخلية ثم محدودة:

| البوابة | الشرط |
|---|---|
| الاستقرار | انقطاع ≤ 0.5/ساعة/لاعب (p95) على ≥ 20 جهاز مختلف الشركات |
| الجودة | MOS ≥ 4.0، شكاوى الصدى ≤ 1 لكل 100 جلسة |
| التأخير | p95 ≤ 350 ms |
| الانضمام | نجاح ≥ 99% |
| الموارد | CPU/بطارية ضمن الميزانية |
| السيرفر | تحمّل 2× الحمل المتوقع، 24 ساعة بدون تسريب ذاكرة |
| التراجع | قدرة التبديل لـLiveKit بسطر إعداد لمدة ≥ 2 أسبوع بعد الإطلاق |

**آلية التدرج:** علم `mafia.voice` (قائمة بيضاء → ٥٪ → ٢٥٪ → ١٠٠٪)، مراقبة بلوحات، إيقاف فوري عند كسر أي بوابة.

## 17. استراتيجية الاختبار

1. **وحدات:** كل قطعة (`protocol`, `jitter`, `opus wrapper`, `ratecontrol`).
2. **متجهات اختبار البروتوكول:** ملفات ثابتة تتحقق منها كل اللغات (Rust/C#/TS).
3. **Property-based + Fuzzing:** مُحلّل الحزم، مُحلّل رسائل التحكم (`cargo fuzz`).
4. **محاكاة الشبكة:** ضياع (0/2/5/10/20%)، jitter (0–200 ms)، إعادة ترتيب، سقوط المسار، تبديل عنوان (`tc netem` + محاكي داخلي).
5. **جودة الصوت:** إشارات مرجعية (جمل مسجلة) ← ViSQOL (MOS-LQO)؛ **ERLE للصدى:** سيناريو «طرف بعيد يحكي وطرف قريب صامت» ثم قياس الإشارة المتبقية.
6. **مصفوفة أجهزة حقيقية:** جدول بأجهزة/نظم/شبكات (Wi-Fi 2.4/5 GHz، 4G/5G، Bluetooth، سماعات سلكية). **كل جولة تجارب بتسجل: الجهاز، الإصدار، الشبكة، النتيجة، ملاحظة صوتية.**
7. **تحمّل (Soak):** ٢ ساعة، 20 جهاز وهمي + 2 حقيقي، مراقبة ذاكرة/CPU/اتصال.
8. **حمل السيرفر:** أداة `mgvc-cli load` تحاكي غرف كبيرة؛ منحنى CPU مقابل الحزم/ث.
9. **اختبار تجريبي بشري (Dogfooding):** المالك وأصحابه بلعبة المافيا الحقيقية مع نموذج استبيان قصير.

## 19. التشغيل (Operations)

- **النشر:** Docker على الـVPS (نفس أسلوب الحارس و`rewards-api`)، `restart: unless-stopped`، حدود سجلات، منافذ: 443/TCP (WSS خلف nginx)، UDP محدد (مثلاً 7900-7999)، جدار ناري مفتوح لها فقط.
- **النطاق:** `voice.mena-gaming.com`.
- **المراقبة:** Prometheus + لوحة (Grafana أو لوحة إدارة بسيطة عنا): جلسات، غرف، حزم/ث، ضياع، jitter، معالج، ذاكرة، أخطاء. **تنبيه** إذا مجرى الأخطاء ارتفع.
- **السجلات:** JSON، بدون محتوى صوت، تدوير.
- **التراجع:** نشر بإصدارات موسومة؛ التراجع بسطر.
- **السعة:** جدول أسبوعي (متكلمون متزامنون، ذروة داتا)؛ عند 60% معالج أو 50% باقة → خطة توسع (VPS أكبر أو سيرفر ثاني بمنطقة قريبة، اختيار حسب ping).
- **المناطق:** نبدأ بمنطقة واحدة. التوسع: العميل يقيس ping لعدة عناوين ويختار الأقرب (توكن يحمل قائمة).

## الملحق أ — مواصفة البروتوكول v0 (مسودة للتثبيت بـM0/M1)

### أ.1 ترويسة حزمة الصوت: عميل → سيرفر (16 بايت، AAD)

| الإزاحة | الحجم | الحقل | الوصف |
|---|---|---|---|
| 0 | 1 | `ver_type` | 4 بت إصدار (=1) + 4 بت نوع |
| 1 | 1 | `flags` | bit0=DTX، bit1=talkspurt start، bit2=FEC، bit3=PTT |
| 2 | 1 | `level` | مستوى −dBov (0=عالٍ … 127=صامت) |
| 3 | 1 | `codec` | 4 بت مدة الإطار + 2 بت قنوات + 2 احتياطي |
| 4 | 4 | `seq` | تسلسل (u32، يبدأ عشوائياً) |
| 8 | 4 | `ts` | ختم زمني بوحدات 48 kHz |
| 12 | 4 | `session` | معرّف الجلسة (من welcome) |
| 16… | n | `payload` | Opus |
| … | 16 | `tag` | وسم Poly1305 |

الأنواع: `0 HELLO`, `1 WELCOME`, `2 AUDIO`, `3 FEEDBACK`, `4 PING`, `5 PONG`, `6 BYE`.

**التشفير:** مفتاح لكل اتجاه من `welcome`. `nonce(12) = salt(4) || seq_u64`. AAD = الترويسة. نافذة replay 128 حزمة.

### أ.2 سيرفر → عميل (20 بايت)
نفس الترويسة، `session` تصبح `source_id` (معرّف المتكلم داخل الغرفة)، وبعدها `ctr` u32 (عدّاد الحزم لهذا المستمع لاستخدامه بالـnonce). السيرفر بيحتفظ بـ`seq/ts` الأصلية للمتكلم لتشغيل jitter buffer.

### أ.3 FEEDBACK (عميل→سيرفر، كل ثانية)
`received`, `lost`, `jitter_ms`, `rtt_ms`, `concealed_ratio`, `transport(udp|tcp)`, `battery_saver`. السيرفر يمرر للمتكلم خلاصة ليكيّف معدل البت.

### أ.4 رسائل التحكم (JSON، أمثلة)
```json
{"t":"join","token":"...","proto":[1],"device":{"os":"android","model":"SM-S928B","sdk":34},"want":{"publish":true}}
{"t":"welcome","session":123456,"udp":{"host":"voice.mena-gaming.com","port":7901},"keys":{"c2s":"...","s2c":"...","salt_c2s":"...","salt_s2c":"..."},"room":{"name":"official:1001","peers":[{"id":"PF...","name":"..."}]}}
{"t":"permissions","can_publish":true,"listen_only_to":null}
{"t":"peer_state","id":"PF...","publishing":true,"muted_by_admin":false}
{"t":"error","code":"token_expired"}
```

### أ.5 آلة حالة العميل
`Idle → Connecting(control) → Handshake(udp) → Connected → [Reconnecting → Connected | Failed]`. `Reconnecting`: محاولة تلقائية بتأخير أُسّي (0.5 → 1 → 2 → 4 ث) مع نفس الجلسة إن أمكن (هجرة)، وإلا توكن جديد.
